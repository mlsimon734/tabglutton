# Repository Guidelines

The one-line rules in this file are load-bearing; the measured histories behind them live in `docs/ENGINEERING.md`. **Before touching bridge, clip, permission, or icon code, read the matching section there** — several of these rules exist precisely because a plausible simplification once undid the fix they pin.

## Project Structure & Module Organization

This is a Bun-powered TypeScript WebExtension for Zen Browser, Firefox, and Chrome; the product is "Tabglutton". Core logic lives in `src/`: `background.ts` wires browser events, `dedup.ts` plans duplicate tab closures (keeper-selection lives in `pickKeeper` here, not in a separate policy module), `normalize.ts` canonicalizes URLs, `storage.ts` handles settings, `clip-current.ts` is the Defuddle-based content extractor injected into pages by Devour, `clip-format.ts` builds the Obsidian markdown + frontmatter and the `obsidian://new` URL, and `target.ts` exposes `IS_CHROME` / `IS_FIREFOX` for the few places that need to branch by target. The agent bridge (see `docs/BRIDGE.md`) lives in `bridge-protocol.ts` (wire contract, shared with the sidecar), `bridge-client.ts` (loopback WebSocket client + alarm-driven reconnect), `bridge-methods.ts` (the six tool implementations), and `undo-log.ts` (close/undo trail). Popup UI files are in `popup/` — `lib.ts` builds the list model both surfaces render, and **duplicate sets lead that list _instead of_ appearing in their host groups, so every tab renders exactly once**: selection, keyboard nav, and every bulk action derive their id list from that grouping, and a tab rendered twice would hand `tabs.remove` a repeated id (which Chrome rejects as a whole batch — see below). Options UI files are in `options/`, the cross-browser `obsidian://` launch shim is in `redirect/`, and static assets are in `icons/`. `manifest.json` defines the Firefox shape and is patched in memory for Chrome. `build.ts` accepts `--target=firefox|chrome|all` and writes `dist-firefox/` or `dist-chrome/`; treat `dist-firefox/`, `dist-chrome/`, `.dev-profile*`, and `web-ext-artifacts/` as generated output.

## Cross-browser build

- Sources stay shared. `src/target.ts` is checked in with `TARGET = "firefox"`. For the Chrome build, `build.ts` overwrites the compiled `dist-chrome/src/target.js` to flip the constant — sources are never mutated.
- Chrome uses `webextension-polyfill` so the `browser.*` call sites keep working. The Chrome service worker is bundled with `Bun.build` (polyfill inlined). Popup/options HTML pages get `<script src="../vendor/browser-polyfill.js"></script>` injected before the module script tag.
- Chrome manifest differences (applied in memory in `build.ts`): drop `browser_specific_settings`, swap `background.scripts` → `background.service_worker`, swap SVG icons → PNG (`icons/icon-chomp-{16,32,48,128}.png`, rasterized by `bun scripts/rasterize-icons.ts`), set `minimum_chrome_version: "120"` (116 covers the MV3 features, but 116-119 clamp extension alarms to a one-minute minimum — the bridge's reconnect alarm is 30s and an agent's first call only waits 45s, so a sleeping worker there answers "no browser is connected" before the alarm ever fires; unpacked builds never reproduce it, their floor is 1s).
- **The app icon is the extension's own mark, drawn twice, and the store's copy of it is not in the package.** `icons/icon-chomp.svg` duplicates the geometry of `icons/logo-mark.svg` (an icon rasterizes standalone and cannot import the mark), as does `docs/media/promo-tile.html`; `tests/logo-mark.test.ts` pins the copies to each other. Sizes 16/32 come from `icons/icon-chomp-small.svg` (chips dropped deliberately — the test pins that too), 48/128 from the full drawing: **regenerate with `bun scripts/rasterize-icons.ts`, never all four from one source.** Firefox needs per-size entries in both `action.default_icon` and `icons`. AMO never reads the manifest's `icons` key — the listing icon and screenshots are Developer Hub uploads (`docs/STORE.md` §5). History: `docs/ENGINEERING.md` §Icons.
- Chrome has no `tab.hidden` and no `getBrowserInfo`; `storage.ts` defaults `scope` to `"current-window"` on Chrome, `background.ts` short-circuits `probeHeuristic` and the `hidden: false` query branch, and the options page hides the scope radio group.
- Chrome rejects the Firefox-only `tabs.onUpdated` filter argument (`{ properties: [...] }`) with "This event does not support filters" — at top level that aborts service-worker registration. `background.ts` registers through the `onTabUpdated` helper, which drops the filter on Chrome (the callbacks already guard on `changeInfo.status`).
- `clip-current.js` is injected as a content script via `scripting.executeScript({ files })`. Chrome validates it with `base::IsStringUTF8`, which — unlike plain UTF-8 validity — rejects Unicode noncharacters / unpaired surrogates (e.g. a raw `U+FFFF` the minifier emits inside a Defuddle regex range), reporting "It isn't UTF-8 encoded." `build.ts` escapes those to `\uXXXX` after bundling (`escapeChromeUnsafeCodePoints`); Firefox skips the check.
- **The `obsidian://` handoff launches through the extension-origin page `redirect/obsidian-redirect.html` on both engines**, never a direct `tabs.create` — a browser-initiated launch has no page principal to remember the external-protocol grant against, and onboarding (same origin) bootstraps the one-time approval, so clips fire silently after. **That approval step is conditional**: onboarding's sequence is a list of step keys, not a count, and picking the file destination at step 2 drops the approval step out of it — a walkthrough that files to disk never needs the grant, and one that files to Obsidian must never lose it. Keep the Firefox dev scripts free of protocol-handler pref overrides, and delete `./.dev-profile*` once if they ever carried them — the prefs persist. The `expectedUrl` passed to `ensureTabReady` is load-bearing: without it the 500ms cleanup and the next clip's clipboard write race the handoff. History: `docs/ENGINEERING.md` §Obsidian launch.
- **The clip destination is chosen, never inferred, and the two engines take different download handles.** `clipDestination` picks Obsidian (default) or a markdown file in the download folder; nothing ever switches on the user's behalf, because a refused `obsidian://` launch is indistinguishable from a successful one and a fallback would be a guess. **The bridge's `tab_clip` obeys the same setting as the popup's Devour** (`clipDestinationFor` in `storage.ts`) **and the same Zotero routing** (`zoteroDestination` in `background.ts`, injected into `bridge-methods.ts` as `routesToZotero` so the Connector's wire details stay in `src/zotero.ts` alone) — an agent clearing a backlog files papers where the user's own clicks would have ([#50](https://github.com/mlsimon734/tabglutton/issues/50)). Same function, **not** the same precondition: Devour wakes a tab before asking and the bridge must not, so it refuses a discarded tab outright and a still-navigating one can still answer translator-less and file as a note (`docs/BRIDGE.md` §Zotero routing). One stated exception, and it outranks both: a `vault` override names Obsidian for that call, because it is a destination the caller asked for outright. A Connector that cannot answer fails the tab with `zotero-failed` and never falls through to Obsidian — that fallthrough would be the silent misfiling the routing exists to prevent. File mode reuses `clipNotePath` from `clip-format.ts` — same base folder, same `site-rules.ts` subfolder, same per-platform note name — and `clip-file.ts` only adds what the downloads API rejects outright (empty components, leading/trailing dots, `..`, backslashes) plus `.md`; its folder segments go through the note name's own `sanitizePathSegment` too, since only the name is sanitized upstream and a base folder is free text the user typed. **Gecko's downloads schema refuses a `data:` URL and a Chrome MV3 service worker has no `URL.createObjectURL`**, so `downloadUrlFor` branches on `IS_CHROME`; the object URL is revoked only after the download settles. The Gecko half is measured, verbatim on Firefox 134.0.2: `Type error for parameter options (Error processing url: Error: Access denied for URL data:text/markdown;base64,…) for downloads.download` — and it is a **synchronous** throw from schema validation, not a rejected promise, so a `.catch()` alone never sees it. `saveClipFile` waits for `state: "complete"` before returning because a clip closes the tab on success and this is the one destination that can _normally_ prove the file exists — attach the `onChanged` listener before reading `downloads.search`, for the reason `ensureTabReady` documents. **Normally, not always, and the difference is reported rather than smoothed over.** When `downloads.search` finds no record the download has been erased, which includes erased _failures_, so that branch has observed nothing: it stays fail-open (never a throw) but answers `confirmed: false` with no path, and both callers then keep the tab — the popup reports it, the bridge sends `confirmedBy: "nobody"` and Gullet declines the close. A guarantee stated above its real strength is the exact failure `docs/ENGINEERING.md` §Clip verification exists to prevent.
- **An extraction too thin to be a clip is measured in one place and refused by whoever would write.** Devour's phase 1 wakes a whole backlog, which is the traffic pattern most likely to draw a bot check, and a challenge served at the parked URL has no translator — so it falls past the Zotero route and Defuddle's "Just a moment…" files as a successful clip that then closes the tab ([#49](https://github.com/mlsimon734/tabglutton/issues/49)). `src/clip-guard.ts` measures every extraction and flags the ones under `MIN_CLIP_CONTENT_CHARS` of visible text, applied at `clipTab` in `background.ts` because that is the single point both the popup's Devour and the bridge's `tab_read`/`tab_clip` extract through — a guard per destination would be three guards, and the destination is not what is wrong. **Length is the detector and the signature list is not**: every interstitial variant is thin and no list of them stays current, so a signature match only sharpens the sentence shown for a page the floor has already flagged, and can never flag one by itself. Where the verdict is acted on, the disposition is the undo invariants' — keep the tab, say why, let the user clear the challenge and retry. Three rules hold it together:
  - **`ok` goes false and the refused text moves onto the verdict.** Two guardrails, not one: a caller that writes branches on `ok` and stops, and a caller that ignores `ok` finds no `payload` to file — reaching the junk text means naming `guarded`, which is the point at which you have read why it is there. Do not put it back on `payload` for convenience.
  - **Refusing is the writer's act, so the caller says.** Devour and `tab_clip` refuse; **`tab_read` does not** — it files and closes nothing, and refusing would cost an agent every legitimately short page with no override, to withhold text it can judge for itself. It gets the text plus a `thin` note (`ThinReadNote`, additive on the wire). `readTab`'s `refuseThin` decides, and both of its extract calls check the verdict: the retry after a no-injection-target error is the likeliest way to meet a challenge, since that is what a page swapping documents reports.
  - **The verdict is read before site access is questioned.** The injection ran and the page answered, so naming a missing grant there would describe a page we had just read.

  The floor's two constraints are in its doc comment; when they disagree it moves up, never down.

- **The `downloads` grant is optional and revocable, and every surface degrades to a stated fact rather than an opaque failure.** It is run-global, so `clipSelectedTabs` answers it **once, before phase 1 wakes anything** — checked per tab, after the wake, a revoked grant reloads an entire backlog to fail every page of it (measured both ways on Chrome 151; the before is in `docs/ENGINEERING.md` §Host permissions). The run comes back `blocked: "downloads-revoked"` with no failures — but **only when nothing in it could have gone anywhere else**: Zotero routing files papers through the Connector, which needs no `downloads`, so a run with routing on is let through and only its file-bound tabs fail. Two more claims are deliberately weak: `downloadsGrant()` answers `unknown` for a `permissions.contains` that threw and every caller then carries on as before (a branch that _writes_ must never act on a question we failed to ask), and a grant revoked _mid-run_ is named per tab from the catch that has already failed. **The remedy every gesture-less surface names is real only because the options page reverts the destination to Obsidian on load** (`onboarding.ts` does the same in `init`): re-selecting an already-checked radio fires no `change`, so a file radio left checked is a destination that can never ask again. The user-facing sentences live in `permissions.ts` so the four surfaces cannot drift.
- **`options_ui.open_in_tab` is a static manifest value, and the two engines want opposite defaults.** The source manifest declares `false` for Firefox (the embedded form is the one choice an extension can't produce at runtime), `build.ts` patches Chrome back to `true` (its embedded render is an unusable modal), `options.ts` hides the `#optionsLayout` section on Chrome, and `openOptionsUi` short-circuits on `IS_CHROME` before reading the setting. The page detects browser-chrome embedding via `window.top !== window.self`. History: `docs/ENGINEERING.md` §Options page.
- **Host permissions are required on Firefox and optional on Chrome, from one source manifest** — `build.ts` deletes `host_permissions` for Chrome and declares `optional_host_permissions` instead, so the install prompt stays quiet and the submission stays out of manual review; `src/permissions.ts` asks at the two moments a click is available (the popup's Devour, enabling the bridge in options). Four rules are measured, not assumed — full story in `docs/ENGINEERING.md` §Host permissions:
  - `requestOrigins` must be the first `await` in the handler — any earlier extension-API await spends Chrome's transient activation — and no `contains()` pre-check goes in front of it.
  - The `hasOrigins` fallback on a `false` or a throw carries Firefox entirely (Gecko rejects `permissions.request` for origins declared in `host_permissions`, even from a real gesture). Do not simplify it away.
  - A missing grant is not a probe miss: it never advances `PROBE_MISSES_BEFORE_DIALLING_BLIND`, and the grant is read once per page and cached — `permissions.contains` resets Chrome's 30s MV3 idle timer, and per-tick checks kept the worker resident for as long as the bridge was enabled. `permissions.onAdded` / `onRemoved` invalidate the cache.
  - The bridge cannot ask for anything (no gesture): `readTab` checks the grant only after extraction has already failed and reports `not-enabled` with the remedy.

- `web-ext lint` is Firefox-only tooling; the `lint:ext` script lints `dist-firefox/` only. The Chrome zip is validated by the Chrome Web Store upload flow.
- Chrome assigns a **new tab id** when it discards a tab (verified on 150: `chrome.tabs.discard(766110265)` returns a tab with id `766110267`). Firefox keeps the id. Any flow that lists tabs and acts on them later — which is the whole shape of a bridge triage run — can therefore meet ids that no longer resolve even though the tabs still exist, so `bridge-methods.ts` appends `STALE_ID_HINT` to every "no such tab id" error rather than letting it read as "the tab was closed."
- **Tab grouping is usable on Zen, and it costs the undo log nothing** — measured on Zen 1.21.14b (Firefox 153.0.4) by `scratch-chrome/verify-groups-zen.ts`, which is the answer to [#33](https://github.com/mlsimon734/tabglutton/issues/33). `tabs.group()` **does not churn tab ids** (`[3,4,5,6,7]` before and after, all still resolvable), so nothing here reaches `undo-log.ts` or the bridge methods that list tabs and act on them later. It **does not wake a discarded tab** either: a discarded `https://example.com` tab was still `discarded: true` after being grouped, which is what makes rule-based grouping viable at backlog scale rather than a 700-page load. Two constraints, both measured: `tabGroups.*` needs a `"tabGroups"` permission or the namespace is simply absent (`tabs.group` stays a function, which is what the absence looks like from the inside), and **grouping silently unpins a pinned tab** — so a rule pass must exclude pinned tabs or say that it unpins. Version floors are already cleared: `tabs.group` is Firefox 138 / Chrome 88 and `tabGroups` is Firefox 139 / Chrome 89, against a declared `strict_min_version` of 140 and `minimum_chrome_version` of 120.
- **Waking a discarded tab is `tabs.reload()`, not `tabs.update({ discarded: false })`** — the latter is inconsistent across Firefox versions. `ensureTabReady` in `background.ts` owns this for both the popup's Devour (`clipTab({ wake: true })`) and the bridge's `tabs_load`, and it attaches its `onUpdated` "complete" listener _before_ reading the tab, not after: `tabs.get` is an IPC round trip, and a tab that finishes loading during it would fire into a listener that does not exist yet and then sit until the timeout. For the mirror-image reason it reads no status back _after_ the reload — `tabs.reload` resolves before the navigation starts, so a read there still reports the pre-reload `"complete"` and would call a tab ready just as it blanks out.
- **"Missing host permission for the tab" does not mean what it says.** It is Gecko's catch-all for an injection that returned no results at all: a frame mid-navigation, or the permanently-restricted `extensions.webextensions.restrictedDomains` hosts (AMO, SUMO, FxA…), which no grant an extension can hold ever lifts. `readTab` retries once after 250ms, then reports the engine's own message plus `NO_INJECTION_TARGET_HINT` — never a "retry this call" remedy a restricted page can never satisfy. Keep the grant check ahead of the retry, and don't gate the retry on "we just ran `tabs_load`". Measurements: `docs/ENGINEERING.md` §Restricted injection.
- **Neither engine gives you a tab's real URL until its navigation commits**, and they disagree about what you get instead: Chrome reports `url: ""` with the target parked in the Chrome-only `pendingUrl`; Gecko reports `about:blank`. Read URLs through the `tabUrl` helper in `bridge-methods.ts` — any new code reading `tab.url` on Chrome needs the same fallback, or a mid-load tab silently vanishes from `tabs_list` and, far worse, from the undo log. History: `docs/ENGINEERING.md` §Uncommitted URLs.
- **Chrome's `tabs.remove` rejects the whole batch at the first id that no longer resolves — having already closed everything ahead of it.** `parseTabsCloseParams` dedupes before anything acts; `removeTabs` treats a rejection as a demotion, not an answer: retry each id alone, then ask the browser which ids still exist. Absence is the signal, not the retry's own result. History: `docs/ENGINEERING.md` §Batch removal.
- **Never open a WebSocket at a port that has not answered, and give the dial its own long deadline.** Gecko's `FailDelayManager` penalizes failed WebSocket connects (delay ×1.5 per failure, 60s ceiling, erased by one success) and applies the delay before the TCP connect, invisibly. Three consequences, all load-bearing — history and the diagnosis playbook are in `docs/ENGINEERING.md` §FailDelay:
  - `BRIDGE_DIAL_TIMEOUT_MS` stays 120s, twice the penalty ceiling. Two shorter builds each wedged the bridge permanently against a sidecar answering `curl` in half a millisecond.
  - The fast-retry burst arms only after losing an established connection, never after a dial that failed to land.
  - `BridgeClient` probes with plain HTTP first and dials only when Gullet's marker names the protocol; a markerless response never gets a token proof. The probe is never a gate (after `PROBE_MISSES_BEFORE_DIALLING_BLIND` misses it dials blind — one candidate per eligible tick), idle-loop misses never count toward it, and the miss counter is deliberately instance-only: a durable counter was tried and reverted the same session after rebuilding a near-ceiling penalty.

- **`manifest.json` must keep its explicit `content_security_policy.extension_pages`.** Firefox's _default_ MV3 extension CSP includes `upgrade-insecure-requests`, and that directive rewrites WebSocket URLs too — `ws://127.0.0.1:4589/` silently becomes `wss://`, loopback included. The bridge sidecar then receives a TLS ClientHello, so Bun's `fetch` handler never runs and the connection is invisible from _both_ ends: nothing logged in gullet, and the extension sees only close code **1015** (TLS handshake failure). Declaring `"script-src 'self'; object-src 'self'"` explicitly drops the directive and the dial succeeds. If bridge connections start failing with 1015, this key is the first thing to check.
- **The "first `tabs_list` of a session times out" report ([#27](https://github.com/mlsimon734/tabglutton/issues/27)) is diagnosed, not fixed, and both of its hypotheses are measured out.** At 1000 tabs in one window the whole `init()` pass costs ~30ms on Gecko and the 249 KB listing serializes in 0.2ms, and two calls back to back after an extension reload answered in 16ms and 44ms — neither startup contention nor response size is within 1000× of 45,000ms. What produces that shape is a browser that stops reading its socket, and on current code the hub's heartbeat converts it into a `no-connection` inside 40s rather than a 45s `timeout` (measured with `SIGSTOP`). **Do not wrap `tabs_list` in a retry**: it would hide the one signal a fresh report needs. Numbers, caveats, and the harnesses: `docs/BRIDGE.md` §Open questions.
- **Bridge requests are served concurrently, so anything browser-global needs a queue.** `storage.local` has no compare-and-swap — the undo log's read-await-write was a lost update that closed tabs with no batch left to undo. Every undo-log access runs through `withUndoLog` (`src/serialize.ts`), `undo_close` holds the lock across its restores, and the Obsidian handoff queue guards the OS clipboard the same way. A new bridge method touching shared state gets a queue, not a hope. History: `docs/ENGINEERING.md` §Concurrency.
- **Nothing is closed that the undo log could not put back.** Each close path pairs tabs with `ClosedTabEntry` values before removing anything, leaves unrecordable tabs open (reported `skipped`), and writes the batch before the removal — then reconciles afterwards so the newest batch never describes a live tab, because that orphan is exactly what the next bare `undo_close` reaches for. `closed` always equals `entries.length`. History: `docs/ENGINEERING.md` §Undo invariants.

- **Clip memory records intent, and "clipped" is the only word for it.** `src/clip-memory.ts` remembers every successful clip under `normalizeUrl`'s key (dedup's canonicalizer, so one page reached two ways is one memory), through a `serialize.ts` queue like the undo log. How well a filing is known is `launched` or `verified`, **derived from a `verifiedAt` timestamp rather than stored as a flag** — a sighting is never taken back, and it must never be re-dated to a later clip that saw nothing. **Only the browser watching a download complete or Gullet finding the note in the vault produces one** — the popup's Obsidian handoff never can, so no surface may say "in your vault". `clip_confirm` (in `BRIDGE_SIDECAR_METHODS`, deliberately not `BRIDGE_METHODS`, which is Gullet's MCP routing table) is how Gullet raises it, and nothing here is a claim about disk _now_. History: `docs/ENGINEERING.md` §Clip memory.

- **Never log a `Settings` object.** It carries `bridgeToken`, which is the entirety of the bridge's authentication — anything holding it can list, read, clip, and close every tab. The startup line in `background.ts` printed it on every wake of the event page, which on this project means continuously, into a console whose contents get pasted wholesale into bug reports and agent sessions. It goes through `loggableSettings` now; a token that has been through a logged build should be regenerated in the options page. **The options page's "Copy diagnostics" block answers to the same rule, one step stricter**: it is assembled field by field in `collectDiagnostics` rather than spread from `settings` — a spread publishes the token today and whatever field is added to `Settings` next — and `DiagnosticsFacts` in `src/diagnostics.ts` is the complete vocabulary of what a paste can contain. The bridge error log records a kind from a closed set plus a port or a bridge method name, **never a caught error's message**: the clip and load paths quote the URL they failed on. There is no redaction pass and must not be one; the guarantee is that there is nothing to redact.

## Gullet (agent bridge sidecar)

`gullet/` is a sibling package, not part of the extension bundle: an MCP server over stdio on one side, a loopback WebSocket hub on the other. It shares `src/bridge-protocol.ts` with the extension so both ends are typechecked against one definition; its agent-only listing renderer is `gullet/src/tabs-view.ts`, not extension source. It has its own `gullet/tsconfig.json` (`lib: ES2022`, `types: bun-types` — no DOM, no `browser`) and zero dependencies. It is excluded from the extension `tsconfig.json`'s `include`, so it never reaches `dist-*`; `bun run build:gullet` instead bundles the executable and shared modules for the `tabglutton-gullet` npm package. Setup and troubleshooting live in `gullet/README.md`.

Global Gullet settings live at `${XDG_CONFIG_HOME:-$HOME/.config}/tabglutton/config.json`, with the token in a separate `0600` file by default. The config is deliberately safe to commit: an inline `"token"` key is rejected even when a CLI or environment token would otherwise win. Keep the additive token precedence (`--token` → env → `tokenCommand` → `tokenFile` → default file → `./.env`). **`./.env` is last on purpose and must not move back up**: it is the only token source read out of a directory the user did not choose — an MCP host sets this process's cwd to whatever project the agent session started in — so above the global file a cloned repo silently replaces the token the options page wrote, putting the session in a realm its author can also join. Last, it can only supply a token nothing else had, and it answers only when the global file is absent (ENOENT), never when reading it merely failed. `tokenCommand` is bounded and lazy; its timeout/nonzero error, including stderr, goes through `Supervisor.fault()`, and the supervisor retries with backoff so unlocking a secret manager heals the existing MCP session. Do not move command execution ahead of that recoverable startup path.

**A clip is confirmed on disk before anything is closed, and `confirmedBy` in the result names who could confirm it — `browser`, `gullet`, or `nobody`.** For a file clip that is the browser, which was seen to complete the download, so Gullet verifies nothing: its check would be the same fact from further away, against a name `conflictAction: "uniquify"` may have changed. A **Zotero** clip is the browser too and is likewise unverified here, for a stronger reason — Gullet does not speak to Zotero at all, and the Connector's `status: "saved"` is the same evidence the popup closes a routed tab on; a save that did not resolve fails the call rather than arriving as a result. `destination: "zotero"` carries no `file` and no `vault`, and an unrecognised destination deliberately falls to the Obsidian branch, where a close nothing can justify is refused. For an Obsidian clip nobody in the browser can — a refused `obsidian://` launch is indistinguishable from a successful one — so `clip-verify.ts` answers and upgrades `nobody` to `gullet`. **`nobody` is fail-open, never an error, and it means different things about the tab in the two destinations**: an unverifiable Obsidian clip is still closed (the handoff was never observable, so that is the pre-verification behaviour standing), while an unverifiable file clip keeps its tab, because that destination _can_ prove itself and this time did not. Every clause below was measured, and the full essay is `docs/ENGINEERING.md` §Clip verification:

- `clipAndVerify` owns the close for **both** destinations: clip with `close: false`, verify if there is anything to verify, then `tabs_close` — and that close is allowed to fail (`closed: false` with a reason, never a failed `tab_clip` that would provoke a duplicate re-clip). `close: false` goes out before the destination is known, because it only comes back in the answer.
- Existence is not proof. The note must be fresher than a timestamp sampled before the request (with `CLIP_MTIME_SLACK_MS`), `isClipNoteName` matches `obsidian://new`'s numbered no-overwrite variants by exact string, attribution reads the note's `source` property (`noteSourceUrl`), and `contentHash` — SHA-256 of exactly what was handed to Obsidian, `\r\n` folded to `\n` — identifies the invocation when everything else collides. One note vouches for one clip.
- An empty note is never a landed clip (Obsidian creates the file and fills it a beat later). Every clip reporting `mismatched` means byte-identity broke somewhere — that verdict exists as its own answer on purpose.
- Inability to check is never a failure: `unknown` is fail-open, only `ENOENT` means "not written", and only a listable folder provably lacking the note is `missing`. State the guarantee at its real strength — "a failed handoff can never cost the user the tab" is false in both directions and must not come back.

The launch bug in [#18](https://github.com/mlsimon734/tabglutton/issues/18) is fixed at its source: Firefox now launches from the same extension-origin redirect page the onboarding approval belongs to, rather than from the browser/system principal, and the Firefox dev scripts no longer pre-approve the protocol through hidden prefs. That fixes the rememberable handoff; it does **not** make browser-side delivery observable. A user can still refuse or revoke the external-protocol grant, the popup still has no sidecar with which to check the vault, and Gullet's verification remains the only confirmation that a bridge clip reached disk.

Tests that stand up a real socket bind to port 0 for an ephemeral port. Diagnostics in gullet go to **stderr only** — stdout is the MCP transport and a stray `console.log` corrupts the session.

**The stdio pump dispatches requests concurrently and serializes only the writes.** Awaiting each dispatch froze the whole session for the length of every call — including the `notifications/cancelled` that could have interrupted it. Out-of-order replies are fine (JSON-RPC matches on `id`); interleaved bytes are not, and in Bun the write **callback** is the only honest completion signal, so `serveStdio` chains writes itself. `McpTransport` is injectable purely so the concurrency is testable. History: `docs/ENGINEERING.md` §stdio pump.

**Gullet elects a hub across the ordered, append-only `BRIDGE_PORT_CANDIDATES`; later processes attach as peers and proxy through it.** Losing the port is not fatal — nothing guarantees one Gullet per session (a single `codex` process was observed spawning two). Peers live in their own map and are never targets for bridge methods; probe before peer attachment, since a markerless local service must never receive a token proof. The election must settle or say why: `start()` bounds the **wait** (`ELECTION_START_TIMEOUT_MS`), not the election; the reason publishes via `Supervisor.fault()`, and `ToolContext.startupError` is a function so every tool call re-reads it — a port freed mid-session heals in place. History: `docs/ENGINEERING.md` §Hub election.

**The hub that wins is a detached process, not the session that spawned it** ([#29](https://github.com/mlsimon734/tabglutton/issues/29)) — that is what makes the browser's connection predate the agent session instead of being discovered at the start of every one. `gullet/src/detached.ts` owns both halves; full story in `docs/ENGINEERING.md` §Detached hub.

- **The spawn is never a single point of failure.** A spawn that throws, or a child that does not answer within `SPAWN_WAIT_MS`, falls through to the in-process binding sweep — exactly what Gullet did before — and stops being retried after `DETACH_ATTEMPTS`. `--no-detach` pins the old shape and is the right flag when debugging, since it puts the hub's logs back on this process's stderr.
- **The token crosses on stdin, never argv**, which `ps` publishes; `--detached-hub` therefore resolves no token source of its own. Its stderr goes to `$XDG_STATE_HOME/tabglutton/hub.log`, truncated per hub generation.
- **A live socket is no longer proof that anyone is waiting.** That inference is what justified the extension pinning its event page (`KEEPALIVE_PING_MS`), and a hub that outlives sessions breaks it. The hub counts sessions (peers, plus its own MCP half unless detached) and publishes the number on the `hello-ack` and on every change; `bridge-client.ts` arms the keepalive **and its own heartbeat** only above zero. Two rules are load-bearing: an **absent** count means entitled, because a hub old enough not to send one dies with its session anyway; and the heartbeat has to stop too, since on Chrome a WebSocket message is itself MV3 activity and a 20s beat would pin the worker forever — which is why the hub also drops to `BRIDGE_IDLE_HEARTBEAT_MS` while idle, and re-checks its connections the instant a session arrives. Measured on Firefox 134 against a real detached hub: with no session the connection turned over at t+1s, t+33s and t+93s; with one attached the same id was held for 120s unbroken; on its departure the socket dropped immediately and the churn resumed.
- **A protocol bump cannot retire a running detached hub.** `shouldRetireFor` runs only after a peer has proved the token, and the proof is protocol-shaped (`deriveProof` hashes role and port), so a newer sidecar's proof can never verify at an older hub — and neither end dials it anyway, because `probeCandidate` classifies another protocol's marker as `incompatible`. The old hub therefore holds its port until it idles out. This is inherent, not an ordering bug: moving the retirement check above the proof check would let any local process retire the hub. Handled diagnostically instead — Gullet's exhaustion fault names the port and `pkill -f "gullet.*--detached-hub"`, and the extension reports `incompatible-sidecar` in both port modes. **Every `BRIDGE_PROTO` bump needs that step in its release notes.** History: `docs/BRIDGE.md` §Wire protocol.
- **A detached hub exits by itself** after `DETACHED_HUB_IDLE_EXIT_MS` (6h) with no session attached, and **retires for a newer peer** — peers send `gullet` on the hello, and only a detached hub ever stands aside (retiring a session-scoped one would take its own agent down with it). Without that, an upgrade would leave the old hub serving stale code for as long as sessions kept arriving, since each one resets the idle clock. `compareGulletVersions` treats an unreadable version as equal rather than coercing it, so a prerelease can never retire a release — and `GULLET_VERSION` in `gullet/src/version.ts` is now load-bearing rather than cosmetic.

## Build, Test, and Development Commands

- `bun install`: install dependencies.
- `bun run build`: build both `dist-firefox/` and `dist-chrome/`.
- `bun run build:gullet`: bundle the publishable `tabglutton-gullet` executable.
- `bun run build:firefox` / `build:chrome`: single-target builds.
- `bun run typecheck`: typecheck the extension (`typecheck:ext`, `tsconfig.test.json` over `src/` + `tests/`) then the sidecar (`typecheck:gullet`).
- `bun run test`: run the Bun test suite under `tests/` and `gullet/tests/`.
- `bun run format` / `format:check`: run oxfmt over the tree (or check only).
- `bun run lint`: runs `lint:js` (oxlint) then `lint:ext` (Firefox `web-ext lint`).
- `bun run check`: typecheck + format:check + lint + test. Run before committing.
- `bun run start`: build firefox and launch Zen with the extension loaded from `dist-firefox/`.
- `bun run start:firefox`: build firefox and launch regular Firefox with a persistent dev profile.
- `bun run start:chrome`: build chrome and launch Chromium via `web-ext --target=chromium`.
- `bun run package`: produce both `tabglutton-firefox-<version>.zip` and `tabglutton-chrome-<version>.zip` in `web-ext-artifacts/`.
- `bun run package:gullet`: build and dry-run the publishable `tabglutton-gullet` package.

## Coding Style & Naming Conventions

Use TypeScript ES modules with explicit relative `.js` import specifiers, as in `import "./normalize.js"`. Keep strict typing clean under `tsconfig.json`; unused locals, unused parameters, implicit `any`, and switch fallthroughs are disallowed. Follow the current two-space indentation, double-quoted strings, trailing commas in multiline calls, and small exported functions/interfaces. Use kebab-case for filenames (`keep-newest.ts`) and camelCase for functions and variables.

## Testing Guidelines

Pure-module unit tests live in `tests/` and run via `bun test`. Each test file mirrors a module name (`normalize.test.ts`, `dedup.test.ts`, `clip-format.test.ts`, `storage.test.ts`, `bridge-protocol.test.ts`, `undo-log.test.ts`, `serialize.test.ts`). Scope is intentionally limited to pure logic — browser-API surfaces (`background.ts`, `bridge-methods.ts`, `bridge-client.ts`, async `storage` helpers, the Defuddle content script) are exercised via `bun run start` or `bun run start:firefox` in a live browser. The bridge's `tabs_load` follows that split: the batch cap and dedup are tested in `bridge-protocol.test.ts`, its MCP routing in `gullet/tests/tools.test.ts`, and the reload itself is live-only. Sidecar tests live in `gullet/tests/`; `hub.test.ts` is the one exception to the pure-logic rule, standing up a real loopback socket to cover the handshake and request routing end to end. Concurrency invariants are unit-testable and are tested: `serialize.test.ts` covers the queue that guards the undo log (including a reproduction of the interleave that loses a batch without it), and `mcp.test.ts` drives `serveStdio` through a fake `McpTransport` to prove a slow call does not delay a `ping` and that two replies never write at once. Test files are typechecked through `tsconfig.test.json` but excluded from `dist/` (the build still uses base `tsconfig.json`).

**`tsconfig.json` and `tsconfig.test.json` restate the same `include` list, and TypeScript replaces rather than merges it on `extends` — so a new top-level directory added to one is silently unchecked by the other.** `bun run typecheck` runs the _test_ config, so a source file reachable by the build but missing from `tsconfig.test.json`'s list typechecks clean and then fails the build. Caught live when `probe/` was added: `bun run check` passed and `bunx tsc --outDir dist-firefox` failed on the same file. Add a new directory to **both** — with one deliberate exception in the other direction: `tsconfig.json` is what the build compiles, so a directory the build must never emit belongs in the **test config only**. `scripts/` is listed there and not in `tsconfig.json` for exactly that reason; adding it to both would ship the release tooling into `dist-*/`.

CI (`.github/workflows/ci.yml`) runs typecheck → test → format:check → oxlint → web-ext lint → package on every push and PR. Locally, `prek install` wires fast format/lint hooks into pre-commit; see `.pre-commit-config.yaml`.

## Version Control

This repo uses [jj](https://github.com/martinvonz/jj) in colocated mode — `.git` and `.jj` coexist, and standard `git` commands work normally on the working tree. **Default to plain `git` commands** (`git status`, `git diff`, `git log`, `git commit`, `git push`) for everyday VCS work. They are well-understood and produce predictable results.

Reach for `jj` only when its unique features are explicitly needed — e.g. `jj op log` / `jj undo` to recover from a mistake, `jj split` / `jj absorb` for hunk-level commit surgery, or `jj describe` to rewrite a description. Do not run `jj bookmark`, `jj rebase`, or other history-rewriting commands without checking with the user first; divergent change-ids and bookmark conflicts are easy to create and hard to clean up non-interactively.

## Versioning

**Which part moves is decided by `BRIDGE_PROTO`, not by whether the change is a feature.** Nothing imports this extension, so strict semver's "new functionality is a minor bump" is a rule for libraries with API dependents and this project has none; the one contract that can actually break a user is the bridge wire protocol an agent harness and Gullet negotiate on. So: **patch** for anything the protocol survives, features included, and **minor** when `BRIDGE_PROTO` bumps or a new capability class lands (the planned triage layer is the next one). `0.4.0` carries an entire new clip destination under that rule, and moves the minor because `BRIDGE_PROTO` went to 3. Gullet's version is kept equal to the extension's so "keep them on the same version" stays followable, and the npm publish rides the same number.

**The CHANGELOG section is written as the work merges, under its real version heading — not at release time, and never under `## [Unreleased]`.** `scripts/release-notes.ts` exits non-zero when a version has no section, so `release.yml` hard-fails on a tag whose notes were never written; accumulating them is what keeps that off release day, when the narrative would have to be reconstructed from diffs. `[Unreleased]` specifically does not work here: the extractor's heading regex requires a leading digit so it never matches, and `release:bump` (`commit-and-tag-version`) prepends its generated section above it, stranding the hand-written content below the new heading — with a near-empty generated section extracted in its place, since the commit subjects here are prose rather than conventional commits. Write bullets flat under `## [<next>](compare-url) (unreleased)` as PRs merge, skip anything with no user-visible effect, reorganize into Features/Breaking/Changed during the release pass, and swap `(unreleased)` for the date then.

Versions are `major.minor.patch.build`, and Firefox accepts **at most four parts**. The first three are the release version and are the only ones that belong in `package.json` / `manifest.json`; the fourth is a counter for signed test builds and is owned entirely by `bun run sign:dev`, which writes it into the artifact and a local git tag and then restores both files. Keeping `package.json` at three parts is also what lets `commit-and-tag-version` work at all — semver has no fourth position.

Committing a four-part version breaks that invariant (it happened once, in `ebbb933 Release 0.1.2.1`). `sign-dev.ts` now slices to the release triple so it cannot emit a five-part version AMO would reject, and counts the build number from `max(highest local tag, any fourth part in package.json)` — AMO requires versions to be unique and strictly increasing, and the tags are local and unpushed, so they are not trustworthy on their own. Bump the release version normally; let the build counter take care of itself.

**The pushed tag is what cuts the GitHub release.** `.github/workflows/release.yml` fires on a three-part `v*` tag, verifies it against `package.json`, runs `bun run check`, packages, and publishes the release with that version's CHANGELOG section as the body — so the GitHub release and the store upload come from one act instead of two. Tag on `main` after the squash merge, not on the release branch, whose commit `main` never gets. Four-part `sign:dev` tags are local and unpushed, and the tag pattern refuses them anyway. To rebuild a release for a tag already pushed, run the workflow manually with the tag as its input. 0.2.0 reached AMO with its tag pushed but no release cut, because this was written down in a checklist nobody re-read rather than here.

## Commit & Pull Request Guidelines

The current history uses a concise imperative subject with optional scope detail, for example `Initial commit: tab dedup extension v1.1 (TypeScript)`. Keep subjects specific and near 72 characters when practical. Pull requests should describe the user-visible change, list verification commands, and mention manifest or permission changes.

**A PR that changes a visible surface carries screenshots in its description — not "when practical".** The surfaces are the popup, the Devour cockpit, options, and onboarding; a diff touching markup or CSS under `popup/`, `options/`, `onboarding/`, or `redirect/` is not reviewable without images, and needs both themes whenever the change reaches the tokens. Prose cannot carry a layout or a contrast decision, the reviewer cannot see one without building and loading the extension, and a description that only _describes_ a redesign is asking to be approved unseen. Capture with the CDP harness rather than an OS window grab — `scratch-chrome/shoot-store.ts` (dark) and `shoot-light.ts` (light), documented in `docs/STORE.md` §5: exact pixel dimensions, no window chrome, no Screen Recording permission, repeatable after the next UI change. That directory is gitignored and local-only, so it will be absent from a fresh clone and from every worktree but the one it was written in; copy it across rather than reinventing it. **The shots are uploaded to GitHub's attachment host, never committed** — a PR that adds megabytes of PNG to the tree is paying for review evidence with every future clone. GitHub has no API for attachments: the web uploader authenticates with a session cookie no token substitutes for, and the CLI team declined to add it ([cli/cli#12960](https://github.com/cli/cli/issues/12960)) because the flow needs a browser to obtain temporary S3 credentials. So drive the browser, which takes about two minutes: open the PR with Claude in Chrome, `find` the comment box's `input[type=file]` and hand it the files with `file_upload` (**never click it** — a click opens a native picker nothing can see), let GitHub's own pipeline write `<img src="https://github.com/user-attachments/assets/<uuid>">` back into the textarea, read those URLs out, **clear the textarea without posting**, and `gh pr edit --body` with them embedded. The URLs outlive the discarded draft. `file_upload` only accepts paths the session has been given, so stage the files in the scratchpad first. **There is no CLI shortcut, and the near-miss is worth knowing**: `POST uploads.github.com/user-attachments/assets` accepts `Authorization: Bearer $(gh auth token)` and answers `201` with a real-looking URL, but that asset then 404s even once a body references it (measured 2026-08-29, token scopes including `repo`) — so a green exit code there proves nothing, and the browser path is the one that produces images that load. Keep a measured before/after table beside the pictures: it states the geometry they only imply, and it still reads if an asset URL ever rots.

## Security & Configuration Tips

Keep browser permissions in `manifest.json` minimal and justify new permissions in the PR. Do not commit generated profiles, packaged zips, or local browser state. WebExtension tooling should always target `dist-firefox/` or `dist-chrome/`, not source directories directly.

`.env` holds **store credentials only**: `WEB_EXT_API_KEY` / `WEB_EXT_API_SECRET` for AMO (`bun run sign`, `sign:listed`, `sign:dev`) and `CWS_PUBLISHER_ID` / `CWS_CLIENT_ID` / `CWS_CLIENT_SECRET` / `CWS_REFRESH_TOKEN` for the Chrome Web Store (`bun run publish:chrome`, minted once by `cws:auth`). Nothing else reads them, they all load through `scripts/sign-env.ts`, and developing, building, and the whole of `bun run check` work without any of them — so a checkout missing `.env` is not a broken checkout. Setup and the API contract are `docs/STORE.md` §7; the Chrome half targets the **V2** API because V1 is supported only until 15 October 2026.
