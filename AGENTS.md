# Repository Guidelines

The one-line rules in this file are load-bearing; the measured histories behind them live in `docs/ENGINEERING.md`. **Before touching bridge, clip, permission, or icon code, read the matching section there** — several of these rules exist precisely because a plausible simplification once undid the fix they pin.

## Project Structure & Module Organization

This is a Bun-powered TypeScript WebExtension for Zen Browser, Firefox, and Chrome; the product is "Tabglutton". Core logic lives in `src/`: `background.ts` wires browser events, `dedup.ts` plans duplicate tab closures (keeper-selection lives in `pickKeeper` here, not in a separate policy module), `normalize.ts` canonicalizes URLs, `storage.ts` handles settings, `clip-current.ts` is the Defuddle-based content extractor injected into pages by Devour, `clip-format.ts` builds the Obsidian markdown + frontmatter and the `obsidian://new` URL, and `target.ts` exposes `IS_CHROME` / `IS_FIREFOX` for the few places that need to branch by target. The agent bridge (see `docs/BRIDGE.md`) lives in `bridge-protocol.ts` (wire contract, shared with the sidecar), `bridge-client.ts` (loopback WebSocket client + alarm-driven reconnect), `bridge-methods.ts` (the six tool implementations), and `undo-log.ts` (close/undo trail). Popup UI files are in `popup/`, options UI files are in `options/`, the cross-browser `obsidian://` launch shim is in `redirect/`, and static assets are in `icons/`. `manifest.json` defines the Firefox shape and is patched in memory for Chrome. `build.ts` accepts `--target=firefox|chrome|all` and writes `dist-firefox/` or `dist-chrome/`; treat `dist-firefox/`, `dist-chrome/`, `.dev-profile*`, and `web-ext-artifacts/` as generated output.

## Cross-browser build

- Sources stay shared. `src/target.ts` is checked in with `TARGET = "firefox"`. For the Chrome build, `build.ts` overwrites the compiled `dist-chrome/src/target.js` to flip the constant — sources are never mutated.
- Chrome uses `webextension-polyfill` so the `browser.*` call sites keep working. The Chrome service worker is bundled with `Bun.build` (polyfill inlined). Popup/options HTML pages get `<script src="../vendor/browser-polyfill.js"></script>` injected before the module script tag.
- Chrome manifest differences (applied in memory in `build.ts`): drop `browser_specific_settings`, swap `background.scripts` → `background.service_worker`, swap SVG icons → PNG (`icons/icon-chomp-{16,32,48,128}.png`, rasterized by `bun scripts/rasterize-icons.ts`), set `minimum_chrome_version: "120"` (116 covers the MV3 features, but 116-119 clamp extension alarms to a one-minute minimum — the bridge's reconnect alarm is 30s and an agent's first call only waits 45s, so a sleeping worker there answers "no browser is connected" before the alarm ever fires; unpacked builds never reproduce it, their floor is 1s).
- **The app icon is the extension's own mark, drawn twice, and the store's copy of it is not in the package.** `icons/icon-chomp.svg` duplicates the geometry of `icons/logo-mark.svg` (an icon rasterizes standalone and cannot import the mark), as does `docs/media/promo-tile.html`; `tests/logo-mark.test.ts` pins the copies to each other. Sizes 16/32 come from `icons/icon-chomp-small.svg` (chips dropped deliberately — the test pins that too), 48/128 from the full drawing: **regenerate with `bun scripts/rasterize-icons.ts`, never all four from one source.** Firefox needs per-size entries in both `action.default_icon` and `icons`. AMO never reads the manifest's `icons` key — the listing icon and screenshots are Developer Hub uploads (`docs/STORE.md` §5). History: `docs/ENGINEERING.md` §Icons.
- Chrome has no `tab.hidden` and no `getBrowserInfo`; `storage.ts` defaults `scope` to `"current-window"` on Chrome, `background.ts` short-circuits `probeHeuristic` and the `hidden: false` query branch, and the options page hides the scope radio group.
- Chrome rejects the Firefox-only `tabs.onUpdated` filter argument (`{ properties: [...] }`) with "This event does not support filters" — at top level that aborts service-worker registration. `background.ts` registers through the `onTabUpdated` helper, which drops the filter on Chrome (the callbacks already guard on `changeInfo.status`).
- `clip-current.js` is injected as a content script via `scripting.executeScript({ files })`. Chrome validates it with `base::IsStringUTF8`, which — unlike plain UTF-8 validity — rejects Unicode noncharacters / unpaired surrogates (e.g. a raw `U+FFFF` the minifier emits inside a Defuddle regex range), reporting "It isn't UTF-8 encoded." `build.ts` escapes those to `\uXXXX` after bundling (`escapeChromeUnsafeCodePoints`); Firefox skips the check.
- **The `obsidian://` handoff launches through the extension-origin page `redirect/obsidian-redirect.html` on both engines**, never a direct `tabs.create` — a browser-initiated launch has no page principal to remember the external-protocol grant against, and onboarding (same origin) bootstraps the one-time approval, so clips fire silently after. Keep the Firefox dev scripts free of protocol-handler pref overrides, and delete `./.dev-profile*` once if they ever carried them — the prefs persist. The `expectedUrl` passed to `ensureTabReady` is load-bearing: without it the 500ms cleanup and the next clip's clipboard write race the handoff. History: `docs/ENGINEERING.md` §Obsidian launch.
- **`options_ui.open_in_tab` is a static manifest value, and the two engines want opposite defaults.** The source manifest declares `false` for Firefox (the embedded form is the one choice an extension can't produce at runtime), `build.ts` patches Chrome back to `true` (its embedded render is an unusable modal), `options.ts` hides the `#optionsLayout` section on Chrome, and `openOptionsUi` short-circuits on `IS_CHROME` before reading the setting. The page detects browser-chrome embedding via `window.top !== window.self`. History: `docs/ENGINEERING.md` §Options page.
- **Host permissions are required on Firefox and optional on Chrome, from one source manifest** — `build.ts` deletes `host_permissions` for Chrome and declares `optional_host_permissions` instead, so the install prompt stays quiet and the submission stays out of manual review; `src/permissions.ts` asks at the two moments a click is available (the popup's Devour, enabling the bridge in options). Four rules are measured, not assumed — full story in `docs/ENGINEERING.md` §Host permissions:
  - `requestOrigins` must be the first `await` in the handler — any earlier extension-API await spends Chrome's transient activation — and no `contains()` pre-check goes in front of it.
  - The `hasOrigins` fallback on a `false` or a throw carries Firefox entirely (Gecko rejects `permissions.request` for origins declared in `host_permissions`, even from a real gesture). Do not simplify it away.
  - A missing grant is not a probe miss: it never advances `PROBE_MISSES_BEFORE_DIALLING_BLIND`, and the grant is read once per page and cached — `permissions.contains` resets Chrome's 30s MV3 idle timer, and per-tick checks kept the worker resident for as long as the bridge was enabled. `permissions.onAdded` / `onRemoved` invalidate the cache.
  - The bridge cannot ask for anything (no gesture): `readTab` checks the grant only after extraction has already failed and reports `not-enabled` with the remedy.

- `web-ext lint` is Firefox-only tooling; the `lint:ext` script lints `dist-firefox/` only. The Chrome zip is validated by the Chrome Web Store upload flow.
- Chrome assigns a **new tab id** when it discards a tab (verified on 150: `chrome.tabs.discard(766110265)` returns a tab with id `766110267`). Firefox keeps the id. Any flow that lists tabs and acts on them later — which is the whole shape of a bridge triage run — can therefore meet ids that no longer resolve even though the tabs still exist, so `bridge-methods.ts` appends `STALE_ID_HINT` to every "no such tab id" error rather than letting it read as "the tab was closed."
- **Tab grouping is usable on Zen, and it costs the undo log nothing** — measured on Zen 1.21.14b (Firefox 153.0.4) by `scratch-chrome/verify-groups-zen.ts`, which is the answer to [#33](https://github.com/mlsimon734/tabglutton/issues/33). `tabs.group()` **does not churn tab ids** (`[3,4,5,6,7]` before and after, all still resolvable), so nothing here reaches `undo-log.ts` or the bridge methods that list tabs and act on them later. It **does not wake a discarded tab** either: a discarded `https://example.com` tab was still `discarded: true` after being grouped, which is what makes rule-based grouping viable at backlog scale rather than a 700-page load. Two constraints, both measured: `tabGroups.*` needs a `"tabGroups"` permission or the namespace is simply absent (`tabs.group` stays a function, which is what the absence looks like from the inside), and **grouping silently unpins a pinned tab** — so a rule pass must exclude pinned tabs or say that it unpins. Version floors are already cleared: `tabs.group` is Firefox 138 / Chrome 88 and `tabGroups` is Firefox 139 / Chrome 89, against a declared `strict_min_version` of 140 and `minimum_chrome_version` of 120.
- **Waking a discarded tab is `tabs.reload()`, not `tabs.update({ discarded: false })`** — the latter is inconsistent across Firefox versions. `ensureTabReady` in `background.ts` owns this for both the popup's Devour (`clipTab({ wake: true })`) and the bridge's `tabs_load`, and it attaches its `onUpdated` "complete" listener _before_ reading the tab, not after: `tabs.get` is an IPC round trip, and a tab that finishes loading during it would fire into a listener that does not exist yet and then sit until the timeout. For the mirror-image reason it reads no status back _after_ the reload — `tabs.reload` resolves before the navigation starts, so a read there still reports the pre-reload `"complete"` and would call a tab ready just as it blanks out.
- **"Missing host permission for the tab" does not mean what it says.** It is Gecko's catch-all for an injection that returned no results at all: a frame mid-navigation, or the permanently-restricted `extensions.webextensions.restrictedDomains` hosts (AMO, SUMO, FxA…), which no grant an extension can hold ever lifts. `readTab` retries once after 250ms, then reports the engine's own message plus `NO_INJECTION_TARGET_HINT` — never a "retry this call" remedy a restricted page can never satisfy. Keep the grant check ahead of the retry, and don't gate the retry on "we just ran `tabs_load`". Measurements: `docs/ENGINEERING.md` §Restricted injection.
- **Neither engine gives you a tab's real URL until its navigation commits**, and they disagree about what you get instead: Chrome reports `url: ""` with the target parked in the Chrome-only `pendingUrl`; Gecko reports `about:blank`. Read URLs through the `tabUrl` helper in `bridge-methods.ts` — any new code reading `tab.url` on Chrome needs the same fallback, or a mid-load tab silently vanishes from `tabs_list` and, far worse, from the undo log. History: `docs/ENGINEERING.md` §Uncommitted URLs.
- **Chrome's `tabs.remove` rejects the whole batch at the first id that no longer resolves — having already closed everything ahead of it.** `parseTabsCloseParams` dedupes before anything acts; `removeTabs` treats a rejection as a demotion, not an answer: retry each id alone, then ask the browser which ids still exist. Absence is the signal, not the retry's own result. History: `docs/ENGINEERING.md` §Batch removal.
- **Never open a WebSocket at a port that has not answered, and give the dial its own long deadline.** Gecko's `FailDelayManager` penalizes failed WebSocket connects (delay ×1.5 per failure, 60s ceiling, erased by one success) and applies the delay before the TCP connect, invisibly. Three consequences, all load-bearing — history and the diagnosis playbook are in `docs/ENGINEERING.md` §FailDelay:
  - `BRIDGE_DIAL_TIMEOUT_MS` stays 120s, twice the penalty ceiling. Two shorter builds each wedged the bridge permanently against a sidecar answering `curl` in half a millisecond.
  - The fast-retry burst arms only after losing an established connection, never after a dial that failed to land.
  - `BridgeClient` probes with plain HTTP first and dials only when Gullet's marker names the protocol; a markerless response never gets a token proof. The probe is never a gate (after `PROBE_MISSES_BEFORE_DIALLING_BLIND` misses it dials blind — one candidate per eligible tick), idle-loop misses never count toward it, and the miss counter is deliberately instance-only: a durable counter was tried and reverted the same session after rebuilding a near-ceiling penalty.

- **`manifest.json` must keep its explicit `content_security_policy.extension_pages`.** Firefox's _default_ MV3 extension CSP includes `upgrade-insecure-requests`, and that directive rewrites WebSocket URLs too — `ws://127.0.0.1:4589/` silently becomes `wss://`, loopback included. The bridge sidecar then receives a TLS ClientHello, so Bun's `fetch` handler never runs and the connection is invisible from _both_ ends: nothing logged in gullet, and the extension sees only close code **1015** (TLS handshake failure). Declaring `"script-src 'self'; object-src 'self'"` explicitly drops the directive and the dial succeeds. If bridge connections start failing with 1015, this key is the first thing to check.
- **Open, unexplained: the first `tabs_list` of a session can time out on a large backlog** (the full 45s `BRIDGE_REQUEST_TIMEOUT_MS`), with an immediate retry succeeding, while the connection is provably fine — do not read it as a reconnect fault. Full brief under "Open questions" in `docs/BRIDGE.md`.
- **Bridge requests are served concurrently, so anything browser-global needs a queue.** `storage.local` has no compare-and-swap — the undo log's read-await-write was a lost update that closed tabs with no batch left to undo. Every undo-log access runs through `withUndoLog` (`src/serialize.ts`), `undo_close` holds the lock across its restores, and the Obsidian handoff queue guards the OS clipboard the same way. A new bridge method touching shared state gets a queue, not a hope. History: `docs/ENGINEERING.md` §Concurrency.
- **Nothing is closed that the undo log could not put back.** Each close path pairs tabs with `ClosedTabEntry` values before removing anything, leaves unrecordable tabs open (reported `skipped`), and writes the batch before the removal — then reconciles afterwards so the newest batch never describes a live tab, because that orphan is exactly what the next bare `undo_close` reaches for. `closed` always equals `entries.length`. History: `docs/ENGINEERING.md` §Undo invariants.

- **Never log a `Settings` object.** It carries `bridgeToken`, which is the entirety of the bridge's authentication — anything holding it can list, read, clip, and close every tab. The startup line in `background.ts` printed it on every wake of the event page, which on this project means continuously, into a console whose contents get pasted wholesale into bug reports and agent sessions. It goes through `loggableSettings` now; a token that has been through a logged build should be regenerated in the options page.

## Gullet (agent bridge sidecar)

`gullet/` is a sibling package, not part of the extension bundle: an MCP server over stdio on one side, a loopback WebSocket hub on the other. It shares `src/bridge-protocol.ts` with the extension so both ends are typechecked against one definition; its agent-only listing renderer is `gullet/src/tabs-view.ts`, not extension source. It has its own `gullet/tsconfig.json` (`lib: ES2022`, `types: bun-types` — no DOM, no `browser`) and zero dependencies. It is excluded from the extension `tsconfig.json`'s `include`, so it never reaches `dist-*`; `bun run build:gullet` instead bundles the executable and shared modules for the `tabglutton-gullet` npm package. Setup and troubleshooting live in `gullet/README.md`.

Global Gullet settings live at `${XDG_CONFIG_HOME:-$HOME/.config}/tabglutton/config.json`, with the token in a separate `0600` file by default. The config is deliberately safe to commit: an inline `"token"` key is rejected even when a CLI or environment token would otherwise win. Keep the additive token precedence (`--token` → env → `./.env` → `tokenCommand` → `tokenFile` → default file). `tokenCommand` is bounded and lazy; its timeout/nonzero error, including stderr, goes through `Supervisor.fault()`, and the supervisor retries with backoff so unlocking a secret manager heals the existing MCP session. Do not move command execution ahead of that recoverable startup path.

**A clip is confirmed on disk before anything is closed, because the browser cannot confirm it** — a refused `obsidian://` launch is indistinguishable from a successful one from inside the extension. Gullet's `clip-verify.ts` answers instead; every clause below was measured, and the full essay is `docs/ENGINEERING.md` §Clip verification:

- `clipAndVerify` owns the close: clip with `close: false`, verify, then `tabs_close` — and that close is allowed to fail (`closed: false` with a reason, never a failed `tab_clip` that would provoke a duplicate re-clip).
- Existence is not proof. The note must be fresher than a timestamp sampled before the request (with `CLIP_MTIME_SLACK_MS`), `isClipNoteName` matches `obsidian://new`'s numbered no-overwrite variants by exact string, attribution reads the note's `source` property (`noteSourceUrl`), and `contentHash` — SHA-256 of exactly what was handed to Obsidian, `\r\n` folded to `\n` — identifies the invocation when everything else collides. One note vouches for one clip.
- An empty note is never a landed clip (Obsidian creates the file and fills it a beat later). Every clip reporting `mismatched` means byte-identity broke somewhere — that verdict exists as its own answer on purpose.
- Inability to check is never a failure: `unknown` is fail-open, only `ENOENT` means "not written", and only a listable folder provably lacking the note is `missing`. State the guarantee at its real strength — "a failed handoff can never cost the user the tab" is false in both directions and must not come back.

The launch bug in [#18](https://github.com/mlsimon734/tabglutton/issues/18) is fixed at its source: Firefox now launches from the same extension-origin redirect page the onboarding approval belongs to, rather than from the browser/system principal, and the Firefox dev scripts no longer pre-approve the protocol through hidden prefs. That fixes the rememberable handoff; it does **not** make browser-side delivery observable. A user can still refuse or revoke the external-protocol grant, the popup still has no sidecar with which to check the vault, and Gullet's verification remains the only confirmation that a bridge clip reached disk.

Tests that stand up a real socket bind to port 0 for an ephemeral port. Diagnostics in gullet go to **stderr only** — stdout is the MCP transport and a stray `console.log` corrupts the session.

**The stdio pump dispatches requests concurrently and serializes only the writes.** Awaiting each dispatch froze the whole session for the length of every call — including the `notifications/cancelled` that could have interrupted it. Out-of-order replies are fine (JSON-RPC matches on `id`); interleaved bytes are not, and in Bun the write **callback** is the only honest completion signal, so `serveStdio` chains writes itself. `McpTransport` is injectable purely so the concurrency is testable. History: `docs/ENGINEERING.md` §stdio pump.

**Gullet elects a hub across the ordered, append-only `BRIDGE_PORT_CANDIDATES`; later processes attach as peers and proxy through it.** Losing the port is not fatal — nothing guarantees one Gullet per session (a single `codex` process was observed spawning two). Peers live in their own map and are never targets for bridge methods; probe before peer attachment, since a markerless local service must never receive a token proof. The election must settle or say why: `start()` bounds the **wait** (`ELECTION_START_TIMEOUT_MS`), not the election; the reason publishes via `Supervisor.fault()`, and `ToolContext.startupError` is a function so every tool call re-reads it — a port freed mid-session heals in place. History: `docs/ENGINEERING.md` §Hub election.

## Build, Test, and Development Commands

- `bun install`: install dependencies.
- `bun run build`: build both `dist-firefox/` and `dist-chrome/`.
- `bun run build:gullet`: bundle the publishable `tabglutton-gullet` executable.
- `bun run build:firefox` / `build:chrome`: single-target builds.
- `bun run typecheck`: typecheck the extension (`typecheck:ext`, `tsconfig.test.json` over `src/` + `tests/`) then the sidecar (`typecheck:gullet`).
- `bun run test`: run the Bun test suite under `tests/` and `gullet/tests/`.
- `bun run format` / `format:check`: run oxfmt over the tree (or check only).
- `bun run lint`: runs `lint:js` (oxlint) then `lint:ext` (Firefox `web-ext lint`).
- `bun run check`: typecheck + format:check + lint + test. Run before committing.
- `bun run start`: build firefox and launch Zen with the extension loaded from `dist-firefox/`.
- `bun run start:firefox`: build firefox and launch regular Firefox with a persistent dev profile.
- `bun run start:chrome`: build chrome and launch Chromium via `web-ext --target=chromium`.
- `bun run package`: produce both `tabglutton-firefox-<version>.zip` and `tabglutton-chrome-<version>.zip` in `web-ext-artifacts/`.
- `bun run package:gullet`: build and dry-run the publishable `tabglutton-gullet` package.

## Coding Style & Naming Conventions

Use TypeScript ES modules with explicit relative `.js` import specifiers, as in `import "./normalize.js"`. Keep strict typing clean under `tsconfig.json`; unused locals, unused parameters, implicit `any`, and switch fallthroughs are disallowed. Follow the current two-space indentation, double-quoted strings, trailing commas in multiline calls, and small exported functions/interfaces. Use kebab-case for filenames (`keep-newest.ts`) and camelCase for functions and variables.

## Testing Guidelines

Pure-module unit tests live in `tests/` and run via `bun test`. Each test file mirrors a module name (`normalize.test.ts`, `dedup.test.ts`, `clip-format.test.ts`, `storage.test.ts`, `bridge-protocol.test.ts`, `undo-log.test.ts`, `serialize.test.ts`). Scope is intentionally limited to pure logic — browser-API surfaces (`background.ts`, `bridge-methods.ts`, `bridge-client.ts`, async `storage` helpers, the Defuddle content script) are exercised via `bun run start` or `bun run start:firefox` in a live browser. The bridge's `tabs_load` follows that split: the batch cap and dedup are tested in `bridge-protocol.test.ts`, its MCP routing in `gullet/tests/tools.test.ts`, and the reload itself is live-only. Sidecar tests live in `gullet/tests/`; `hub.test.ts` is the one exception to the pure-logic rule, standing up a real loopback socket to cover the handshake and request routing end to end. Concurrency invariants are unit-testable and are tested: `serialize.test.ts` covers the queue that guards the undo log (including a reproduction of the interleave that loses a batch without it), and `mcp.test.ts` drives `serveStdio` through a fake `McpTransport` to prove a slow call does not delay a `ping` and that two replies never write at once. Test files are typechecked through `tsconfig.test.json` but excluded from `dist/` (the build still uses base `tsconfig.json`).

**`tsconfig.json` and `tsconfig.test.json` restate the same `include` list, and TypeScript replaces rather than merges it on `extends` — so a new top-level directory added to one is silently unchecked by the other.** `bun run typecheck` runs the _test_ config, so a source file reachable by the build but missing from `tsconfig.test.json`'s list typechecks clean and then fails the build. Caught live when `probe/` was added: `bun run check` passed and `bunx tsc --outDir dist-firefox` failed on the same file. Add a new directory to **both**.

CI (`.github/workflows/ci.yml`) runs typecheck → test → format:check → oxlint → web-ext lint → package on every push and PR. Locally, `prek install` wires fast format/lint hooks into pre-commit; see `.pre-commit-config.yaml`.

## Version Control

This repo uses [jj](https://github.com/martinvonz/jj) in colocated mode — `.git` and `.jj` coexist, and standard `git` commands work normally on the working tree. **Default to plain `git` commands** (`git status`, `git diff`, `git log`, `git commit`, `git push`) for everyday VCS work. They are well-understood and produce predictable results.

Reach for `jj` only when its unique features are explicitly needed — e.g. `jj op log` / `jj undo` to recover from a mistake, `jj split` / `jj absorb` for hunk-level commit surgery, or `jj describe` to rewrite a description. Do not run `jj bookmark`, `jj rebase`, or other history-rewriting commands without checking with the user first; divergent change-ids and bookmark conflicts are easy to create and hard to clean up non-interactively.

## Versioning

Versions are `major.minor.patch.build`, and Firefox accepts **at most four parts**. The first three are the release version and are the only ones that belong in `package.json` / `manifest.json`; the fourth is a counter for signed test builds and is owned entirely by `bun run sign:dev`, which writes it into the artifact and a local git tag and then restores both files. Keeping `package.json` at three parts is also what lets `commit-and-tag-version` work at all — semver has no fourth position.

Committing a four-part version breaks that invariant (it happened once, in `ebbb933 Release 0.1.2.1`). `sign-dev.ts` now slices to the release triple so it cannot emit a five-part version AMO would reject, and counts the build number from `max(highest local tag, any fourth part in package.json)` — AMO requires versions to be unique and strictly increasing, and the tags are local and unpushed, so they are not trustworthy on their own. Bump the release version normally; let the build counter take care of itself.

**The pushed tag is what cuts the GitHub release.** `.github/workflows/release.yml` fires on a three-part `v*` tag, verifies it against `package.json`, runs `bun run check`, packages, and publishes the release with that version's CHANGELOG section as the body — so the GitHub release and the store upload come from one act instead of two. Tag on `main` after the squash merge, not on the release branch, whose commit `main` never gets. Four-part `sign:dev` tags are local and unpushed, and the tag pattern refuses them anyway. To rebuild a release for a tag already pushed, run the workflow manually with the tag as its input. 0.2.0 reached AMO with its tag pushed but no release cut, because this was written down in a checklist nobody re-read rather than here.

## Commit & Pull Request Guidelines

The current history uses a concise imperative subject with optional scope detail, for example `Initial commit: tab dedup extension v1.1 (TypeScript)`. Keep subjects specific and near 72 characters when practical. Pull requests should describe the user-visible change, list verification commands, and mention manifest or permission changes.

**A PR that changes a visible surface carries screenshots in its description — not "when practical".** The surfaces are the popup, the Devour cockpit, options, and onboarding; a diff touching markup or CSS under `popup/`, `options/`, `onboarding/`, or `redirect/` is not reviewable without images, and needs both themes whenever the change reaches the tokens. Prose cannot carry a layout or a contrast decision, the reviewer cannot see one without building and loading the extension, and a description that only _describes_ a redesign is asking to be approved unseen. Capture with the CDP harness rather than an OS window grab — `scratch-chrome/shoot-store.ts` (dark) and `shoot-light.ts` (light), documented in `docs/STORE.md` §5: exact pixel dimensions, no window chrome, no Screen Recording permission, repeatable after the next UI change. That directory is gitignored and local-only, so it will be absent from a fresh clone and from every worktree but the one it was written in; copy it across rather than reinventing it. GitHub's image upload is session-authenticated and unreachable from `gh`, so the shots are committed on the branch — regenerating whatever the change made stale in `docs/media/` is usually the right place for them — and linked from the description by a `raw.githubusercontent.com` URL pinned to a **commit SHA**, which keeps rendering after the branch is deleted on merge.

## Security & Configuration Tips

Keep browser permissions in `manifest.json` minimal and justify new permissions in the PR. Do not commit generated profiles, packaged zips, or local browser state. WebExtension tooling should always target `dist-firefox/` or `dist-chrome/`, not source directories directly.

`.env`'s `WEB_EXT_API_KEY` / `WEB_EXT_API_SECRET` are **release-signing credentials only** — `bun run sign` and `sign:dev` read them and nothing else does. Developing, building, and the whole of `bun run check` work without them, so a checkout missing `.env` is not a broken checkout.
