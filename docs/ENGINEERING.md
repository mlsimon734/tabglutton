# Engineering notes

Verbatim histories migrated out of `AGENTS.md` on 2026-08-12 (its git history holds the original placement). Each section is the measured story behind a one-line invariant that stayed in `AGENTS.md` — read the matching section before changing the code it describes. Nothing here is advisory garnish: most entries exist because a plausible simplification once undid the fix they describe.

## Icons

- **The app icon is the extension's own mark, drawn twice, and the store's copy of it is not in the package.** `icons/icon-chomp.svg` carries the same tab-with-a-cookie-bite silhouette that every UI surface fetches from `icons/logo-mark.svg` at runtime; it once carried an unrelated fanned-pages drawing, and nothing caught it for months because the toolbar icon and the popup header are never in frame together. An icon is rasterized standalone with no stylesheet, so it cannot import the mark — the geometry is duplicated, as it also is in `docs/media/promo-tile.html`, and `tests/logo-mark.test.ts` pins the copies to each other. `icons/icon-chomp-small.svg` is the 16/32 drawing: the chips are sub-pixel at toolbar size and only cost contrast, so it drops them and spends the room on a larger glyph, keeping the silhouette and bite byte-identical (the test pins their absence as deliberate). **Sizes 16 and 32 come from the small drawing, 48 and 128 from the full one — regenerate with `bun scripts/rasterize-icons.ts` rather than by hand, since rasterizing all four from one source is the obvious move and silently discards the per-size work.** Firefox needs per-size entries in both `action.default_icon` and `icons`, which is also what fixes the scaled-down render in `about:addons`. And **AMO never reads the manifest's `icons` key at all**: `Addon.icon_type` is written only by `AddonFormMedia` in addons-server, so the listing icon and screenshots are Developer Hub uploads that change nothing about the package and are changed by nothing in it — 0.2.0 shipped with a placeholder icon and an empty gallery for exactly that reason. See `docs/STORE.md` §5.

## Obsidian launch

- The `obsidian://` clip handoff launches through the extension-origin page `redirect/obsidian-redirect.html` on both engines instead of a direct `tabs.create({ url: "obsidian://…" })`. A browser-initiated launch has no page principal against which Firefox can remember the external-protocol grant (and Chrome has the equivalent limitation). The one-time extension-origin approval is bootstrapped by the onboarding ping (same origin), so clips fire silently after. Keep the Firefox dev scripts free of protocol-handler pref overrides: a fresh profile must exercise the same approval path as a store install. Dropping the `--pref` flags is not retroactive — `--keep-profile-changes` left them written into `./.dev-profile` and `./.dev-profile-firefox`, so delete those once or they keep pre-approving the scheme. The launch tab is opened in the background and closed shortly after, so a clip that _does_ need the prompt drops silently: the approval has to come from onboarding (Settings re-opens it), not from a clip. Firefox also returns a newly created tab as `about:blank` with `status: "complete"` before the requested extension page starts, while Chrome returns `url: ""` with the target in `pendingUrl`; the `expectedUrl` passed to `ensureTabReady` is therefore load-bearing. Without it the helper resolves before the redirect module runs, putting both the 500ms cleanup and the next clip's clipboard write back in a race with the handoff.

## Options page

- **`options_ui.open_in_tab` is a static manifest value**, so the `optionsInTab` setting cannot flip it — and the two engines want opposite defaults. The source manifest declares `false` for Firefox, because the embedded form is the one an extension cannot produce at runtime (nothing lets it navigate to `about:addons`) while a full tab is just a URL; `openOptionsUi` (`src/open-options.ts`) opens that URL for the other choice, raising an already-open settings tab rather than duplicating it, the way `openOptionsPage` does. Declaring `true` instead would leave "show it in the Add-ons Manager" unimplementable. **Chrome honours the same flag but renders a narrow modal on `chrome://extensions`**, which this page does not fit, so `build.ts` patches the Chrome manifest back to `open_in_tab: true`, `options.ts` hides the whole `#optionsLayout` section, and `openOptionsUi` short-circuits on `IS_CHROME` before reading the setting — otherwise a stale stored `false` would summon that modal. Only Tabglutton's own settings buttons route through it; reaching the page from the browser's own Preferences button always renders it embedded, which is why `options.ts` sets an `embedded` class from `window.top !== window.self` and `options.css` drops its page frame there.

## Host permissions

- **Host permissions are required on Firefox and optional on Chrome**, from one source manifest. `manifest.json` declares `host_permissions: ["*://*/*"]`; `build.ts` deletes that for Chrome and declares `optional_host_permissions: ["*://*/*", "http://127.0.0.1/*"]` instead, so the Chrome install prompt says nothing about reading websites — that string ("Read and change all your data on all websites") is both the scariest warning the store renders and what routes a submission into manual review. `src/permissions.ts` asks for the grant at the two moments a click is available: the popup's Devour (`CLIP_ORIGINS`, for injecting the Defuddle extractor) and switching the bridge on in options (`BRIDGE_ORIGINS`, for the loopback probe's cross-origin `fetch`). Dedup needs neither — closing tabs and reading their titles and URLs come from `tabs` — so the default flow is never interrupted. Four things are load-bearing and each was measured, not assumed:
  - **`requestOrigins` must be the first `await` in the handler.** Chrome gates `permissions.request` on the click's transient activation, and awaiting any other extension API first spends it. That is also why there is no `contains()` pre-check in front of it: `request()` already resolves `true` without prompting when the permission is held.
  - **It falls back to `hasOrigins` on a `false` or a throw, and that fallback carries Firefox entirely.** Gecko rejects `permissions.request` for an origin declared in `host_permissions` — verified, verbatim: `permissions.request may only be called from a user input handler` — even from a real gesture. Without the fallback the shared clip path would read that as "user denied" and Devour would be dead on the primary browser. Do not simplify it away.
  - **A missing grant is not a probe miss.** `BridgeClient.hasHostAccess()` gates probing and dialling and latches the `needs-access` status; it deliberately does not advance `PROBE_MISSES_BEFORE_DIALLING_BLIND`, because a blind dial is a failed WebSocket connect and that is the single input to Gecko's `FailDelayManager`. Counting a permission we can see we do not hold would rebuild the exact reconnect penalty the probe exists to avoid, and keep rebuilding it. It re-arms the idle probe instead. The grant itself is read **once per page and cached**: `permissions.contains` is a WebExtension API call, every such call resets Chrome's 30s MV3 idle timer, and the idle loop makes one every 3s — so checking it per tick kept the service worker resident for as long as the bridge was enabled with no sidecar, which is this product's normal state (Gullet lives exactly as long as an agent session). `permissions.onAdded` / `onRemoved` invalidate the cache and tick immediately. The cost is that a change reaching neither event — and `hasOrigins` answers `false` on a throw, which is cached the same way — is no longer picked up within `IDLE_PROBE_MS` but when the page next starts. That is a bounded wait only because the worker now suspends at all: the 30s alarm rebuilds the client on the next wake.
  - **The bridge cannot ask for anything.** It has no gesture, so `readTab` checks `hasOrigins(CLIP_ORIGINS)` only _after_ extraction has already failed (no extra IPC on the hot path) and reports `not-enabled` with the remedy, rather than letting an agent see Chrome's opaque "Cannot access contents of url".

  Verified live on both engines, since none of it is reachable from `bun test`: a clean Chrome profile holds no origins, `executeScript` is genuinely refused, and an enabled bridge reports `needs-access` rather than dialling; a real _signed_ Firefox install (not `web-ext run` or `Addon:Install { temporary: true }`, both of which auto-grant and had been masking the question) holds `["*://*/*"]`, so Devour has never been broken on Firefox and the request call there only matters if the user revokes access in `about:addons`. Chrome carries granted permissions across an extension update, so existing users are not re-prompted — and a dev profile that ever ran the old build cannot show the clean-install state. Harnesses: `scratch-chrome/verify-chrome-permissions.ts`, `verify-zen-permissions.ts`, `verify-zen-real-install.ts`, each on its own throwaway profile.

## Restricted injection

- **`Missing host permission for the tab` does not mean what it says.** Firefox was observed raising it from the first `scripting.executeScript` after `tabs_load` even while `permissions.contains(["*://*/*"])` remained true, with an identical call moments later succeeding (Zen 153.0.1). It is Gecko's catch-all for an injection that came back with **no results at all** — `queryContent` in `toolkit/components/extensions/parent/ext-tabs-base.js` throws it on `!results.length`, carrying Mozilla's own `TODO bug 2047009: This error is misleading when the reason for the lack of results is navigation/removal of all targets`. The content side (`matchesWindowGlobal`) simply skips frames it cannot touch, so unrelated causes arrive as this one string. **The permanently-restricted case is measured, not inferred**: on Firefox 134.0.2, with the grant confirmed held in the same breath (`permissions.contains({ origins: ["*://*/*"] })` → `true`), injecting into `addons.mozilla.org`, `support.mozilla.org`, and `accounts.firefox.com` failed with exactly `Missing host permission for the tab` in **both** shapes `clipTab` uses (`func` and `files`), while `example.com` in the same run injected into 1 frame. Those hosts come from `extensions.webextensions.restrictedDomains` (read from the browser, twelve entries — the Mozilla add-on, support, accounts, and sync properties), and no grant an extension can hold lifts them, so a `tab_read` of such a tab fails permanently no matter how often it is retried. The other cause, a frame mid-navigation, is the likeliest reading of the original `tabs_load` observation (the reload replaces the top window global) and stays unmeasured. The wording is exact only for a top-frame injection: `ext-scripting.js` sets `frameIds = [0]` for a plain `{ target: { tabId } }` call, and anything else appends `" or frames"` (also measured, via `allFrames: true`), which `isNoInjectionTargetError` matches too. Harness: `scratch-chrome/verify-restricted-injection.ts`, on its own throwaway profile. `readTab` therefore retries once after 250ms and then reports **the engine's own message plus `NO_INJECTION_TARGET_HINT`** — never a "retry this call" remedy, which is advice a restricted page can never satisfy. Keep the grant check ahead of the retry so a genuinely revoked permission still returns `not-enabled`, and do not gate the retry on "we just ran `tabs_load`": the navigation race belongs to any tab that moves during a read, and `readTab` has no cross-call state to gate on anyway.

## Uncommitted URLs

- Neither engine gives you a tab's real URL **until its navigation commits**, and they disagree on what they give you instead. Chrome reports `url: ""` and parks the target in the Chrome-only `pendingUrl`; Gecko reports `about:blank` (verified on Zen 1.21.9b) and exposes the target nowhere. So a tab caught mid-load looked address-less on Chrome — silently dropped from `tabs_list` and, far worse, from the undo log, making that one close unreversible. `bridge-methods.ts` reads both fields through the `tabUrl` helper; any new code reading `tab.url` on Chrome needs the same fallback. On Gecko the same close records `about:blank` and reopens blank, which is a limitation, not a bug we can fix — triage acts on tabs from a listing, which have long since committed.

## Batch removal

- Chrome's **`tabs.remove` rejects the whole call on a duplicate id** ("No tab with id: N") — the first removal succeeds, the second finds nothing — so a batch containing the same id twice closes the tab _and_ reports failure. `parseTabsCloseParams` deduplicates before anything acts on the list. Dedup is not the whole fix, because **a batch removal is not all-or-nothing**: Chrome removes in order and rejects at the first id that no longer resolves, so the tabs ahead of it are closed and the ones behind it are not — and a stale id (which Chrome mints on every discard) takes that same path without any duplicate involved. `removeTabs` in `bridge-methods.ts` therefore treats a rejection as a demotion, not an answer: it retries each id alone and then asks the browser which ids still exist. **Absence is the signal, not the retry's own result** — a tab the batch call already took rejects the retry too, and reading that as "still open" would drop its undo entry, which is the one close `undo_close` could never reverse.

## FailDelay

- **Never open a WebSocket at a port that has not answered, and give the dial its own long deadline.** Gecko delays reconnects to an endpoint that has been refusing (`network.websocket.delay-failed-reconnects`) and applies that delay _before_ issuing the TCP connect, so the socket sits in CONNECTING with nothing for `lsof` to see. The mechanism is `FailDelayManager` in `netwerk/protocol/websocket/WebSocketChannel.cpp`, and its numbers are what make the rest of this tractable: the delay grows x1.5 per failed connect from 200-400ms, is **capped at 60s** (`kWSReconnectMaxDelay`), is measured from the _last_ failure, and is deleted outright by one successful connect. Only failed **WebSocket** connects feed it — a plain HTTP request is not one, and closing a socket before it has connected is explicitly excluded (`NS_ERROR_NOT_CONNECTED`). So the thing that actually accumulates a penalty is a re-dial loop hammering an empty port: 8 fast retries per wake is ~9 failures per 30s and reaches the ceiling inside a minute, where the 30s alarm alone would take ~7. Three consequences, all load-bearing:
  - `BRIDGE_DIAL_TIMEOUT_MS` is 120s — twice the ceiling — and bounds only a socket that neither opens nor errors. Two shorter builds (5s, then 25s) each wedged the bridge permanently against a sidecar answering `curl` in 0.47ms with a `101`, while the build with _no_ dial deadline connected fine, just slowly (~70s, the delay at the time). `BRIDGE_HANDSHAKE_TIMEOUT_MS` (5s) is a separate deadline, armed on `open`.
  - The fast-retry burst is armed **only after losing an established connection**, never after a dial that failed to land. Having just been connected is the only proof we get that something is there to retry into.
  - `BridgeClient` probes with `fetch("http://127.0.0.1:<port>/")` before opening a socket and dials only when Gullet's marker names the supported protocol. A markerless response is foreign and is never handed a browser identity or proof. This keeps the penalty at zero rather than merely survivable: without it an enabled bridge with no sidecar sits at the 60s ceiling after ~7 idle minutes, and because the ceiling is measured from the last failure while we re-dial every 30s, the first connect of a session lands anywhere in 0-60s — the "stuck on Connecting…" symptom, produced with every part of the bridge healthy. The probe is never a gate: after `PROBE_MISSES_BEFORE_DIALLING_BLIND` misses it dials anyway, so a `fetch` blocked by some future local-network rule degrades to the old behaviour instead of to a bridge that never dials at all. And because probing is free in exactly the way a dial is not, discovery no longer waits on the alarm: while the page is awake an idle loop rotates one candidate every 3s (`IDLE_PROBE_MS`), so a sidecar started mid-session is found in seconds rather than within one alarm period — which is what used to lose the session-start race against `BRIDGE_CONNECT_WAIT_MS` (now 45s, one full period plus real slop). The 30s alarm remains the backstop that survives page suspension, and idle-loop misses never count toward dialling blind — only ticks from outside the loop do (the alarm, a page wake, `sync()`, a fast retry): a blind dial is a failed WebSocket connect, the one thing that feeds the penalty, and one eligible tick may blind-dial only one candidate. The miss counter is deliberately instance-only and dies with the page: a durable counter (`storage.session`) was tried so the valve would fire "reliably" across suspensions, and it accumulated wake-time misses fast enough to rebuild a near-ceiling reconnect penalty within ~15 minutes — observed live as `bridge socket open after 48129ms` against a healthy sidecar — so it was reverted the same session. (That browser was later caught failing socket creation browser-wide — its own Push service logging `NS_ERROR_SOCKET_CREATE_FAILED` — so the counter may not own that 48s alone; see the open question in `docs/BRIDGE.md`. The revert stands either way: blind dials are the only penalty input we control.) Suspension resetting the count is what keeps blind dials rare; the valve still counts to four during real awake use, the only world where escaping a blocked `fetch` helps.

  Diagnosing an accumulated delay: a _constant_ timeout is the tell (a real connect failure varies, a deadline does not), the socket's own `error` arrives **after** our abort, and the browser can still reach the port over plain HTTP — loading `http://127.0.0.1:4589/` in a tab renders Gullet's `403 Forbidden` instantly. Prove the server independently with `curl -i --http1.1 -H "Upgrade: websocket" -H "Connection: Upgrade" -H "Sec-WebSocket-Version: 13" -H "Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==" -H "Origin: moz-extension://x" http://127.0.0.1:4589/`. The delay is in-memory, so restarting the browser clears an accumulated one. But a FailDelay hold is capped at 60s and ends in a normal connect — `bridge dial timed out after 120000ms` hitting the full deadline repeatedly, with no SYN visible in `lsof` and the server healthy, is a different animal: browser-wide socket dysfunction (the Browser Console shows Firefox's own Push service failing with `NS_ERROR_SOCKET_CREATE_FAILED`), observed live in a ~1,050-tab Zen and cleared only by restarting the browser. See the reproduction in `docs/BRIDGE.md`'s open questions before touching any bridge constant over it.

## Concurrency

- **Bridge requests are served concurrently, so anything browser-global needs a queue.** `bridge-client.ts` dispatches every frame as its own `void this.onMessage(...)`, and hub/peer election exists precisely so several agent sessions drive one browser at once — two `tabs_close` calls genuinely interleave. `storage.local` has no compare-and-swap, so the undo log's read-await-write was a lost update: both callers read the same log, both appended their batch, the second write dropped the first, and those tabs were closed with no batch left for `undo_close` to find. Every undo-log access now runs through `withUndoLog` (`src/serialize.ts`), and `undo_close` holds it across its restores rather than just its critical sections — that also makes a double undo of one batch safe, since the second caller re-reads inside the lock. The same primitive backs the Obsidian handoff queue, which guards the OS clipboard for the same reason. A new bridge method touching shared state gets a queue, not a hope.

## Undo invariants

- **Nothing is closed that the undo log could not put back.** `tabs_close` pairs each tab with its `ClosedTabEntry` before removing anything and leaves an unrecordable tab open (reported as `skipped`) rather than closing it off the end of the log; `tab_clip({ close: true })` holds the same invariant. Ids that no longer resolve come back as `missing`, and `closed` always equals `entries.length` — a listing-then-acting tool must never report more closed than it can reverse. The converse matters just as much: the batch is written _before_ the removal, so anything that then fails to close leaves the log describing a live tab, and `undo_close` with no id takes the **newest** batch — that orphan is precisely what the next undo reaches for, reopening a duplicate of a tab that never went anywhere. Both close paths reconcile: `tabs_close` narrows the batch to what `removeTabs` confirms is gone (the rest join `skipped`), and `tab_clip({ close: true })` checks whether the tab survived a rejected `tabs.remove` before deciding to drop its batch or report the close.

## Clip verification

**A clip is confirmed on disk before anything is closed, because the browser cannot confirm it.** A refused `obsidian://` launch is indistinguishable from a successful one from inside the extension: the ephemeral launch tab sits at `about:blank` with `status: "complete"` in both cases, raises no dialog and fires no error (measured on Firefox 134 with the scheme's `network.protocol-handler.*` prefs both set and unset — the tab samples are byte-identical). So `openObsidianUrl` reports the path it _intended_ to write, a dropped handoff read as success, and `tab_clip({ close: true })` would close the tab over a note that was never saved — a close `undo_close` can reverse, but the clip itself is simply gone. Gullet can answer what the browser cannot, because it runs beside the vault and already reads Obsidian's registry: `clip-verify.ts` resolves the vault directory and looks for the note. Six things are load-bearing. **The close is taken away from the extension**: `clipAndVerify` requests the clip with `close: false`, verifies, and only then calls `tabs_close`, so the undo batch is still written by the one method that owns it and `batchId` keeps its meaning — and that close is allowed to fail. The note is already on disk by then, so a tab that went away or was renumbered during verification comes back as `closed: false` with a reason, never as a failed `tab_clip`: an agent told the clip failed re-clips it, and Obsidian writes the duplicate. **Existence is not proof** — re-clipping a page that was already filed would find the _old_ note and vouch for a handoff that never happened, so the note must have been written since a timestamp sampled before the request, with `CLIP_MTIME_SLACK_MS` absorbing the gap between our clock and the filesystem's. **`obsidian://new` never overwrites**: handed a name that is taken it writes `Note 1.md`, then `Note 2.md` (verified live), and since the extension only ever reports the name it _asked_ for, checking that one path called a landed clip missing the second time a page was filed — `isClipNoteName` matches the numbered variants, by exact string comparison because a note title may contain regex metacharacters. **A note is attributed, not merely counted**: two same-titled pages clipped concurrently ask for the same name and both timestamps precede both writes, so freshness alone let the dropped clip claim the note the other one wrote — and close its tab over nothing. The note says which page it holds, in the `source` property `markdownForClip` writes, so `verifyClip` takes the clipped tab's URL and a note recording a different page never vouches. That needs no shared state, so it holds across the hub/peer processes a claim map cannot reach. `noteSourceUrl` reads the value to the _last_ quote on the line, because the writer escapes `"` and nothing else; the format is duplicated rather than imported (clip-format's import graph reaches browser-typed code, and Gullet has no DOM) and `tests/clip-source.test.ts` pins the two together. Only positive disagreement disqualifies — an unparseable note falls back to freshness, so drift costs a defence rather than failing real clips. Behind that, **one note still vouches for one clip**: the verifier spends each note path+mtime once, which is all that is left when two clips of the _same_ page race. **The clip's own text is what closes the last gap.** Two _processes_ clipping one URL simultaneously defeat both of the above — same source, and the claim maps are not shared — so `tab_clip` returns `contentHash`, the SHA-256 of exactly what it handed Obsidian, and a note that does not hash to it was written by some other clip. That identifies the invocation rather than the destination, needs no marker in the user's notes, and holds across processes. It rests on a measurement, not an assumption: `obsidian://new` was handed known bytes and the file compared, in both clip modes, at 238 B and 50 kB, in the `test` vault and in both of the user's real (plugin-bearing) vaults — byte-identical every time, no trailing newline added, no line endings rewritten, no truncation. **That measurement is macOS-only, and one platform is known to break it**: in the default clipboard mode the text crosses the _OS clipboard_, and Windows carries plain text as `CF_UNICODETEXT` with CRLF, so the note on disk has endings the extension never composed. Both hashers therefore fold `\r\n` to `\n` first (`src/clip-hash.ts`, `clipContentHash` in `clip-verify.ts`) — line endings are transport, not content, and the cost is only the ability to tell apart two clips that differ in nothing else. **If byte-identity fails for any other reason the symptom is every clip reporting `mismatched`**, which is why that verdict exists as its own answer and says so in its message. The hash is never required: an older extension sends none and attribution falls back to `source`. The extension hashes with WebCrypto and Gullet with Bun's hasher, so `tests/clip-source.test.ts` pins the two implementations together — importing the extension's real helper rather than restating it, since a restated copy would prove only that Bun agrees with the test — and nothing else would catch an encoding, digest, or normalization change, whose symptom would again be every clip unconfirmed. That test is also why the hash lives in its own pure module instead of in `bridge-methods.ts`, whose import graph reaches `browser`. **An empty note is never a landed clip**: Obsidian creates the file and fills it a beat later (measured live in both real vaults), and without that guard the empty file is exactly the one with no parseable `source`, which the fallback would have read as ours. **State the guarantee at its real strength**: hashed, a `landed` verdict means this exact text is on disk; unhashed, only that a fresh note for this page is; and it means nothing at all when the check cannot run, because `unknown` is fail-open and the pre-verification behaviour stands there, dropped handoffs included. "A failed handoff can never cost the user the tab" is false in both directions and must not come back. **Inability to check is never a failure**: an unreadable registry, an unknown vault name, an unlistable folder, or an unstattable note returns `unknown` and behaviour falls back to what it was, the same soft contract as the vault-override check — only `ENOENT` means "not written", which is why `readDir`/`modifiedAt` distinguish absent from unreadable rather than collapsing both to `null`. Only a folder that exists and provably lacks the note is `missing`. For the same reason `parseObsidianVaultEntries` stores the registry's **exact** path and trims only the copy the vault name is derived from: a trailing space is a legal directory name on macOS and Linux, and a trimmed path checks the wrong directory.

## stdio pump

The stdio pump dispatches requests **concurrently and serializes only the writes**. Awaiting each dispatch before reading the next line froze the whole session for the length of every call — including `ping` and `notifications/cancelled`, so a cancellation could not arrive during the only work it could cancel — and these calls are long by design (`BRIDGE_CONNECT_WAIT_MS`, a 30s `tabs_load` batch). Out-of-order replies are fine, JSON-RPC matches on `id`; interleaved _bytes_ are not, and a `tabs_list` frame for a few hundred tabs is far past any pipe's atomic-write size. Node's Writable would queue chunks in call order, but this is Bun over a pipe and this area has already cost days on assumed platform behaviour, so `serveStdio` chains writes itself. `write()` there returns `false` for backpressure while still completing, so the **callback** is the only honest "this chunk is gone" signal. `McpTransport` is injectable purely so the concurrency is testable.

## Hub election

Gullet elects a **hub** across the ordered, append-only `BRIDGE_PORT_CANDIDATES`: every round discovers a same-token hub across the full set before binding, then binds in canonical order; a lost bind is re-probed before moving on. This prevents both concurrent-start and late-free-port split brains. A numeric `--port` keeps the single-candidate fixed path. The process that binds serves the browser, and later ones attach as **peers** (`backend.ts` → `peer.ts`, wire types in `peer-protocol.ts`) and proxy their MCP calls through it, so several agent sessions share one browser connection. Do not reintroduce "losing the port is fatal" — nothing guarantees one Gullet per session, and a single `codex` process was observed spawning two, with its MCP client bound to the loser. Peers live in their own map and are never targets for a bridge method. Probe before peer attachment: a markerless local service must never receive a token proof.

The election must **settle, or say why**. `main` awaits `backend.start()` before `serveStdio`, so a loop that only ever exits on winning means the MCP server never answers `initialize` when the port is held by something that will never authenticate — another service, or a Gullet carrying a different token. That is the exact hang the `startupError` path exists to replace, reached by a different road, and it silently undid `b98b94b` when the Supervisor was introduced. So `start()` bounds the **wait** (`ELECTION_START_TIMEOUT_MS`), not the election: it throws when the deadline passes while the election carries on underneath with a backing-off gap. The reason is published on `Supervisor.fault()` rather than only thrown, and `ToolContext.startupError` is a **function** so every tool call re-reads it — a port that frees up mid-session heals in place instead of leaving the client refusing against a snapshot taken at startup.

## Detached hub

**The hub outlives the session that spawned it, and that is the whole point** ([#29](https://github.com/mlsimon734/tabglutton/issues/29)). Everything the bridge does about discovery — the 3s idle probe loop, the 30s alarm, the 45s `BRIDGE_CONNECT_WAIT_MS` — exists because the hub used to die with its agent session, so every session start re-ran discovery and every session's first WebSocket dial went into a port that had appeared seconds earlier, in a browser that might have been idle for hours. The controlled reproduction on 2026-07-29 is what settled that this is not a discovery problem: the probe loop found the sidecar in **180ms** and the dial then sat in CONNECTING for the full 120s `BRIDGE_DIAL_TIMEOUT_MS`, twice consecutively, with no SYN reaching TCP, in a browser whose own Push service was failing with `NS_ERROR_SOCKET_CREATE_FAILED` at ~1,050 tabs. A standing connection has to win a socket **once per browser session**, not once per agent session. So the first Gullet that finds no hub spawns one that is nobody's child and attaches to it as a peer — the path every later session already took — and session start becomes a local peer attach. Measured on the real sidecar: session 1 spawned the hub and attached; killing session 1 left the port answering; session 2's `initialize` returned in **41ms** with `attached to the hub` and no election at all.

- **Nothing here may become a single point of failure.** A spawn that throws, or a child that has not answered within `SPAWN_WAIT_MS` (3s — this is a local process start, and the fallback costs milliseconds), returns null and the Supervisor carries straight on into the binding sweep it always had. `DETACH_ATTEMPTS` bounds it at two per process, because an environment where the spawn can never work — a read-only install, a sandbox refusing `fork` — would otherwise start a doomed process on every election round for the life of the session. The fallback is not a degraded mode; it is exactly what Gullet did before this existed, which is also why `backend.test.ts` still runs the whole election suite with `detach: false`.
- **The token goes over stdin.** `argv` is world-readable through `ps` and this token is the entirety of the bridge's authentication. `--detached-hub` therefore resolves no token source of its own — which also avoids re-running a `tokenCommand` in a process with no terminal, where a locked secret manager would block forever.
- **The child's election is deliberately not the Supervisor's.** A session-scoped Gullet that meets an existing hub attaches to it, because it has an MCP client to serve either way; a detached hub that meets one has nothing to offer and exits. That is also what settles two sessions spawning at the same moment: both children start, one binds, the other finds it and goes away.
- **`Bun.spawn({ detached: true, stdin: "pipe" })` + `unref()` really does outlive its parent** — verified on Bun 1.3.14 / macOS before any of this was written (the child reparents to pid 1 and keeps running), and again by `detached.test.ts`, which spawns the real entry from a parent that exits immediately. This repo has paid for assumed platform behaviour more than once; that test exists so this one is not assumed either.

**The honest problem the feature created was the keepalive entitlement, and it was designed before the rest was built.** A live socket _was_ the proof that an agent session existed — Gullet was spawned by a harness and died with it — and that proof is what justified `KEEPALIVE_PING_MS` holding the Gecko event page awake. A hub that outlives every session breaks it in the expensive direction: staying connected around the clock means never suspending, spending wakeups on nobody. So the hub counts sessions (its peers, plus its own MCP half unless detached) and publishes the number on the `hello-ack` and again on every change; the extension arms the keepalive only above zero. Four clauses are load-bearing:

- **Absent means entitled.** A hub old enough not to send a count is one whose lifetime _is_ an agent session, so for it the old inference still holds. Reading the missing field as zero would switch the keepalive off against exactly the hubs that still need it — and the measured cost of no keepalive on Zen 1.21.9b was a socket dropping every 20-60s and taking ~30s to return, so a third of the time there was no bridge at all.
- **The extension's own heartbeat stops too, not just the keepalive.** On Gecko that is merely tidy, since WebSocket traffic resets no idle timer there — which is why the keepalive has to make a real API call in the first place. On Chrome it is the entire other half: a sent or received WebSocket message _is_ activity for an MV3 worker from 116, so a 20s beat into an idle hub would keep the worker resident forever and hand back the exact cost the count was added to avoid.
- **The hub slows its own beat to `BRIDGE_IDLE_HEARTBEAT_MS` (5 min)** for the same reason, comfortably past both engines' ~30s idle timeouts. The resolution loss is bounded and deliberate — a hub with no session has nothing in flight to protect — and when a session attaches, `syncHeartbeat` clears `awaitingPong` and pings immediately rather than waiting a further beat to discover a connection is dead. Clearing first is not optional: a slow beat may have gone out microseconds earlier with its pong still in flight, and dropping a healthy browser over that would be the fix causing the outage it exists to prevent.
- **Idle browser churn is not logged**, because a detached hub is dialled and dropped once per background-page suspension for as long as the browser runs. The roster is logged instead at the moment a session attaches, which is the moment someone is there to read it.

Verified live on Firefox 134.0.2 against a real detached hub, watching connection _identities_ rather than counts (a socket replaced between two polls leaves the count unchanged, which is precisely the case under test): with no session attached the browser connection turned over at **t+1s, t+33s and t+93s** — the page suspending and redialling on its alarm, as an unentitled browser should. With one session attached the same connection id was held for the full **120s** with no turnover. On the session's departure the socket dropped immediately and the churn resumed at t+273s and t+333s.

**A detached hub must be able to go away, in both of the ways it can become unwanted.** It exits after `DETACHED_HUB_IDLE_EXIT_MS` (6h) with no session attached — chosen against the gaps it has to survive (lunch, an afternoon of meetings, an evening pass) rather than any property of the code, with every attaching session resetting it. And it **retires for a newer peer**: peers send their version as `gullet` on the hello, and a detached hub older than the peer answers `hello-error` with `RETIRING_FOR_NEWER_PEER`, releases the port, and exits. Without that, an upgrade would leave the old hub serving stale code for as long as sessions kept arriving, since each arrival resets the idle clock. Only a _detached_ hub ever retires — retiring a session-scoped one would take its own agent session down with it, which is far worse than serving a version-old peer for a few minutes. `compareGulletVersions` refuses to coerce: a version with any non-numeric component compares as **equal** rather than being parsed part-way, because `parseInt` stops at the first non-digit and would read `1.0.0-beta.2` as a fourth component outranking `1.0.0` — a prerelease retiring the release. That also made `GULLET_VERSION` load-bearing rather than cosmetic; it had been sitting at a stale `0.1.0` against a `0.3.1` package, and now lives in `gullet/src/version.ts` so `backend.ts` can read it without importing `main.ts`.
